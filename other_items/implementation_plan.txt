# CoreTradeGlobal — Admin Dashboard & HubSpot Analytics Panel

## Amaç

Platformun tüm büyüme metriklerini, üye yaşam döngüsünü, site davranışlarını ve HubSpot CRM verilerini tek ekrandan yönetebileceğimiz, gerçek zamanlı veri akışı olan kapsamlı bir **Admin Analytics Dashboard** oluşturmak.

> Mevcut veri kaynakları: Google Analytics 4, Microsoft Clarity, HubSpot CRM, Platform DB (üye veritabanı), LinkedIn outreach logları, E-posta kampanya logları, **Çalışan günlük mesaj giriş sistemi (manuel log)**.

#### 🔑 Üye Kimliği Takibi (Clarity identify API) *← YENİ*

> [!IMPORTANT]
> Bu entegrasyon için Next.js platformuna **tek seferlik** bir kod eklenmesi gerekiyor.
> Üye giriş yaptığı anda Clarity oturumu o üyenin ID’siyle etiketleniyor.
> Bu sonrasında tüm session recording’ler ve heatmap’ler per-user filtrelenebilir hale geliyor.

**Platform'a Eklenecek Kod (Next.js — tek seferlik):**

```javascript
// /app/layout.js veya login sonrası tetiklenen hook'ta
// Üye giriş yaptığında çağrılır:

function identifyUserInClarity(user) {
  if (typeof window !== 'undefined' && window.clarity) {
    window.clarity('identify',
      user.id,           // Benzersiz üye ID (platform DB'den)
      undefined,         // session ID (auto)
      undefined,         // page ID (auto)
      user.email         // okunabilir etiket (Clarity'de görünür)
    );

    // Ek etiketler — Clarity'de filtreleme için
    window.clarity('set', 'membership', 'registered');
    window.clarity('set', 'country',    user.country);
    window.clarity('set', 'sector',     user.sector);
    window.clarity('set', 'plan',       user.plan || 'free');
    window.clarity('set', 'joinDate',   user.createdAt);
  }
}

// Çağrımı:
// useEffect(() => { if (session?.user) identifyUserInClarity(session.user); }, [session]);
```

**Bu Kodun Aktifleşmesiyle Dashboard'da Görülecekler:**

| Clarity’den Gelen Veri | Dashboard’da Kullanım |
|---|---|
| `userId` → platform DB ile eşle | Üye profil kartında Clarity linki |
| Sayfa ziyaret geçmişi | En çok hangi sayfa, kaç dakika |
| Rage/dead click sayısı | UX sorunları hangi üyede daha fazla |
| Oturum sayısı ve süresi | Engagement skoru hesaplama |
| Session recording URL | Tek tıkla Clarity'de o üyenin kaydo |
| Scroll derinliği | Üye gerçekten okuyor mu? |

**Clarity Filtreleme Linki Formatı:**
```
https://clarity.microsoft.com/projects/view/[projectId]/
  recordings?filters=CustomUserId%3D[userId]
```

> [!NOTE]
> Clarity’nin ücretli planlarında (Pro+) Export API’si var;
> ücretsiz planda ise dashboard linki yönlendirmesi kullanılır.
> Demo aşamasında link yönlendirme yeterli; export entegrasyonu ilerleyen aşamada yapılır.

## Bölüm 11 — 🔔 Uyarı & Alert Merkezi

**"Şu an panelde ilgilenmen gereken her şey — tek yerde"**

Farklı sayfalarda dağınık duran uyarıları (churn riski, gecikmiş görev, süresi dolan reklam, eksik team log, düşük NPS trendi, HubSpot senkron açığı, düşük onboarding) tek bir kural motoruyla toplayan merkez. Panelin "yönetim" iddiasını somutlaştıran en önemli bölüm.

**Uyarı Seviyeleri:**

| Seviye | Örnek | Aksiyon |
|---|---|---|
| 🔴 Kritik | Gecikmiş HubSpot görevi 48s+, kritik churn (60g+), güvenlik uyarısı | Hemen ilgilen |
| 🟠 Yüksek | Süresi dolan reklam, eksik team log 3g+, HubSpot senkron açığı >100 | 24 saat içinde |
| 🟡 Orta | Yeni destek talebi, düşen NPS trendi, düşük onboarding tamamlama | Bu hafta |
| 🔵 Düşük | Bilgilendirme, hedef ilerleme, haftalık özet | İnceleme yeter |

**Kural Motoru:**
Her metrik için tanımlanmış eşikler. Örnek:
- `churn_days >= 60` → Kritik uyarı
- `ad.end_date - now() <= 3d` → Yüksek uyarı
- `team_log.missing_days >= 3` → Yüksek uyarı
- `nps.7day_avg < previous_period * 0.9` → Orta uyarı
- `hubspot.orphan_contacts > 100` → Yüksek uyarı

**Uyarı Kartı Özellikleri:**
- Başlık + kategori + seviye
- Detay (hangi üye, hangi konu, hangi metrik)
- "İlgili sayfaya git" linki
- Durum: Aktif / Okundu / Kapatıldı / Ertelendi (snooze — 1s/1g/1h)
- Kim atadı (opsiyonel)

**Ekran Bölümleri:**
- Üst şerit: seviye bazında sayaçlar (kritik/yüksek/orta/düşük)
- Ana liste: filtrelenebilir, sıralanabilir uyarı listesi
- Sağ panel: seçili uyarının detayı ve aksiyon butonları
- Alt: geçmiş uyarılar (kapatılan/çözülen)

**Veri Kaynağı:** Rules engine (kendi backend) → tetikleyiciler tüm bağlı kaynaklardan gelir (Platform DB + HubSpot + Clarity + GA4 + destek modülü). Uyarılar `alerts` tablosunda saklanır.

## Bölüm 19 — 🌍 Ticaret Akış Haritası

**"RFQ → Teklif → Sipariş → Kargo → Teslim zinciri + coğrafi ve sektörel rota görünümü"**

Platformun asıl işini gösteren tek ekran. Şu anki panel üye ve outreach izliyor; bu bölüm platformdaki gerçek ticaretin nasıl aktığını görselleştirir. Alibaba admin panelinin en büyük tek katmanının muadili.

### 6 Aşamalı İşlem Zinciri

```
1. RFQ Oluşturuldu
   ↓
2. Yanıt Alan RFQ (en az bir seller yanıtladı)
   ↓
3. Teklif Verildi (fiyat/koşul netleşti)
   ↓
4. Sipariş Onayı (alıcı kabul etti)
   ↓
5. Kargo Yola Çıktı (satıcı gönderdi)
   ↓
6. Teslim Edildi (alıcı teyit etti)
```

Her aşama için: adet, önceki aşamadan dönüşüm oranı, ortalama geçiş süresi.

### Ana Metrikler

- **Aktif RFQ / Bekleyen Teklif / Aktif Sipariş / Kargoda / Bu Ay Teslim** (üst şerit KPI)
- **RFQ → Sipariş dönüşüm oranı** (marketplace likiditesinin ana göstergesi)
- **Sipariş → Teslim başarı oranı** (operasyonel sağlık)
- **Ortalama süre metrikleri:** RFQ → İlk teklif, teklif → sipariş, sipariş → kargo, kargo → teslim
- **En hızlı / en yavaş işlem süreleri**
- **Takılan işlemler:** RFQ 7g+ yanıtsız, teklif 5g+ karar yok, sipariş 3g+ kargo yok, kargo 30g+ teslim yok (bunlar otomatik Uyarı Merkezi'ne düşer)

### Coğrafi Görünüm

**Ülke → Ülke Ticaret Rotası tablosu (Sankey diyagramına dönüştürülebilir):**

Sütunlar: Satıcı ülkesi | → | Alıcı ülkesi | İşlem sayısı | Ort. süre | Trend (haftalık %)

Kullanım: Hangi rotalar patlıyor, hangi rotalar sönüyor, yeni açılan rotalar (fırsat sinyali).

### Sektörel Akış

Hangi sektör en çok işlem üretiyor, hangi sektörden hangi sektöre çapraz satış var. Kanal (kim satıyor) + hedef (kim alıyor) matrisi.

### Lojistik / Kargo Kanal Dağılımı

- Deniz yolu (konteyner)
- Kara yolu (TIR)
- Hava yolu (kargo)
- Express (DHL, FedEx, UPS)

### 23.1 — Katman 1: İstemci Tarafı (Public Site)

**B) Client-side event batching**

Her kullanıcı aksiyonunda ayrı HTTP isteği atmak yasak. Event'ler tarayıcıda biriktirilir, toplu gönderilir.

```javascript
// lib/analytics/eventBuffer.js
const buffer = [];
let flushTimer = null;

const FLUSH_INTERVAL = 5000;   // 5sn
const MAX_BUFFER     = 20;     // veya 20 event dolunca

export function trackEvent(name, payload) {
  buffer.push({ name, payload, ts: Date.now() });

  if (buffer.length >= MAX_BUFFER) return flush();
  if (!flushTimer) flushTimer = setTimeout(flush, FLUSH_INTERVAL);
}

function flush() {
  if (!buffer.length) return;
  const batch = buffer.splice(0, buffer.length);
  clearTimeout(flushTimer);
  flushTimer = null;

  // sendBeacon: sayfa kapansa bile gider, main thread'i bloklamaz
  const blob = new Blob([JSON.stringify({ events: batch })],
                        { type: 'application/json' });
  navigator.sendBeacon('/api/events', blob);
}

// Sayfa kapanırken kalanları gönder
window.addEventListener('pagehide', flush);
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush();
});
```

**Neden `sendBeacon`?** `fetch`/`XHR` sayfa kapanışında iptal edilir ve main thread'i meşgul eder. `sendBeacon` tarayıcının arka planına devreder, kullanıcı hiç fark etmez.

**C) Reklam impression ölçümü — IntersectionObserver**

Reklam "gösterildi" sayılması için gerçekten görünür olmalı; her render'da değil.

```javascript
// Reklam gerçekten viewport'a girince ve 1sn kalınca say
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting && entry.intersectionRatio >= 0.5) {
      setTimeout(() => {
        if (entry.isIntersecting) {
          trackEvent('ad_impression', { adId: entry.target.dataset.adId });
          observer.unobserve(entry.target);  // bir kez say
        }
      }, 1000);
    }
  });
}, { threshold: [0.5] });
```

Bu hem doğru ölçüm verir hem gereksiz event üretmez.

**D) Performans bütçesi (hard limit)**

Yeni hiçbir özellik bu sınırları aşamaz. CI'da otomatik kontrol edilir (Lighthouse CI).

| Metrik | Hedef | Kırmızı çizgi |
|---|---|---|
| LCP | < 2.5s | 4.0s |
| INP | < 200ms | 500ms |
| CLS | < 0.1 | 0.25 |
| Toplam JS (gzip) | < 300KB | 500KB |
| 3. parti script sayısı | ≤ 4 | 6 |
| Analitik kaynaklı main-thread bloklama | < 50ms | 150ms |

> ⚠️ **Önemli:** Mevcut Core Web Vitals değerleri (Site Analytics bölümüne bakınız) hedeflerin gerisindeyse, yeni izleme kodu eklemeden **önce** mevcut sorunlar giderilmelidir. Aksi halde her ekleme durumu kötüleştirir.

### 23.2 — Katman 2: Yazma Yolu (Write Path)

**Altın kural:** Kullanıcının isteği, analitik yazma işlemini **beklemez**.

**A) Fire-and-forget deseni**

```javascript
// ❌ YANLIŞ — kullanıcı analitik yazımını bekler
export async function POST(req) {
  const order = await createOrder(data);
  await logEvent('order_created', order.id);   // ← gecikme ekler
  await updateEngagementScore(userId);         // ← daha da kötü
  return Response.json(order);
}

// ✅ DOĞRU — analitik kuyruğa atılır, kullanıcı beklemez
export async function POST(req) {
  const order = await createOrder(data);

  // await YOK — kuyruğa bırak, dön
  eventQueue.add('order_created', { orderId: order.id, userId })
    .catch(err => logger.error('queue push failed', err));

  return Response.json(order);
}
```

**B) Kuyruk altyapısı**

```javascript
// lib/queue.js — BullMQ + Redis
import { Queue, Worker } from 'bullmq';

export const eventQueue = new Queue('events', {
  connection: redisConfig,
  defaultJobOptions: {
    removeOnComplete: 1000,   // son 1000 başarılıyı tut, gerisini sil
    removeOnFail: 5000,
    attempts: 3,
    backoff: { type: 'exponential', delay: 2000 }
  }
});

// Ayrı process'te çalışan worker — web sunucusunu meşgul etmez
new Worker('events', async (job) => {
  await db.insert(userEvents).values(job.data);
}, {
  connection: redisConfig,
  concurrency: 10
});
```

**C) Yüksek hacimli sayaçlar — Redis buffer + periyodik flush**

Reklam gösterimi, sayfa görüntülenmesi gibi çok yüksek hacimli olaylarda **her olay için 1 satır yazmak yasak**. Redis'te sayaç tutulur, periyodik olarak toplu yazılır.

```javascript
// Her impression'da: sadece Redis INCR (mikrosaniye)
await redis.hincrby(`ad_impr:${dateHour}`, adId, 1);

// Dakikada bir çalışan flush job — toplu INSERT
async function flushImpressions() {
  const key = `ad_impr:${previousDateHour}`;
  const counts = await redis.hgetall(key);
  if (!Object.keys(counts).length) return;

  await db.insert(adImpressionsHourly)
    .values(Object.entries(counts).map(([adId, count]) => ({
      adId: Number(adId),
      hourBucket: previousDateHour,
      impressions: Number(count)
    })))
    .onConflictDoUpdate({
      target: [adImpressionsHourly.adId, adImpressionsHourly.hourBucket],
      set: { impressions: sql`excluded.impressions` }
    });

  await redis.del(key);
}
```

**Kazanç:** Ham satır sayısı, olay sayısından bağımsız hale gelir. Milyon gösterim de olsa, saatte reklam başına 1 satır yazılır.

**D) Hangi veri ham, hangisi agrege saklanır**

| Veri tipi | Saklama şekli | Gerekçe |
|---|---|---|
| Reklam gösterimi | Saatlik agrege | Tekil gösterim analitik değeri düşük |
| Reklam tıklaması | Ham satır | Hacim düşük, kim tıkladı önemli |
| Sayfa görüntüleme | Günlük agrege (sayfa bazlı) | GA4 zaten detayı tutuyor |
| Üye event'i (login, ilan ekleme, RFQ) | Ham satır | Onboarding funnel + skor için gerekli |
| Mesaj metadata | Ham satır | Yanıt süresi hesabı için gerekli |
| Bildirim gönderimi | Ham satır | Fatigue hesabı için gerekli |

```sql
-- ✅ Tek tablo, indeksli, milisaniyeler içinde döner
SELECT * FROM daily_metrics
WHERE metric_date BETWEEN $1 AND $2
ORDER BY metric_date;
```

**Yerine bunu yapmaz:**

```sql
-- ❌ Her panel açılışında 5 tabloyu tarayan sorgu
SELECT COUNT(*) FROM users WHERE created_at > ...
UNION ALL SELECT COUNT(*) FROM orders WHERE ...
-- (primary DB'yi meşgul eder, site yavaşlar)
```

**B) Materialized view (orta hacimli agregasyonlar için)**

```sql
CREATE MATERIALIZED VIEW mv_member_segments AS
SELECT
  u.id, u.name, u.country, u.sector,
  es.score,
  pf.completeness_pct,
  CASE
    WHEN es.score >= 85 AND u.is_verified THEN 'vip_candidate'
    WHEN es.score <= 30 AND u.last_login < now() - interval '45 days' THEN 'critical_churn'
    WHEN es.score BETWEEN 31 AND 60 THEN 'passive'
    ELSE 'normal'
  END AS segment
FROM users u
LEFT JOIN engagement_scores es ON es.user_id = u.id
LEFT JOIN profile_fill pf      ON pf.user_id = u.id;

CREATE UNIQUE INDEX ON mv_member_segments (id);

-- Gece yenile — CONCURRENTLY sayesinde okuma engellenmez
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_member_segments;
```

**C) API cache katmanı**

// Panel endpoint'leri cache'lenir — aynı sorgu 5dk içinde tekrar çalışmaz

### 23.5 — Katman 5: Cron & Batch İşler

**A) Zamanlama — çakışma yok, düşük trafik saatinde**

| İş | Zaman | Süre hedefi |
|---|---|---|
| Günlük metrik rollup | 02:00 | < 5 dk |
| Engagement skoru hesabı | 02:30 | < 15 dk |
| Segment materialized view refresh | 03:00 | < 5 dk |
| HubSpot senkron diff | 03:30 | < 20 dk |
| Profil doluluk hesabı | 04:00 | < 5 dk |
| Uyarı kural motoru | Her 15 dk | < 30 sn |
| Reklam impression flush | Her 1 dk | < 5 sn |
| SEO / Search Console çekimi | 05:00 | < 10 dk |
| Katalog sağlık taraması | Haftalık, Pazar 03:00 | < 60 dk |

**B) Incremental hesaplama — full recompute yasak**

```javascript
// ❌ YANLIŞ — her gece tüm üyeleri baştan hesapla
const allUsers = await db.select().from(users);
for (const user of allUsers) { await computeScore(user.id); }

// ✅ DOĞRU — sadece değişenleri hesapla
const changed = await db.select({ userId: userEvents.userId })
  .from(userEvents)
  .where(gt(userEvents.createdAt, lastRunAt))
  .groupBy(userEvents.userId);

// Ek olarak: 7 gündür hesaplanmamışları da dahil et (bayatlamayı önle)
const stale = await db.select({ userId: engagementScores.userId })
  .from(engagementScores)
  .where(lt(engagementScores.computedAt, sql`now() - interval '7 days'`));

const targets = [...new Set([...changed, ...stale].map(r => r.userId))];
await processInChunks(targets, 500, computeScore);
```

**C) Chunk'lama ve nefes alma**

```javascript
async function processInChunks(items, size, fn) {
  for (let i = 0; i < items.length; i += size) {
    await Promise.all(items.slice(i, i + size).map(fn));
    await sleep(100);   // DB'ye nefes aldır — connection pool'u boğma
  }
}
```

**D) Job lock — üst üste binmeyi önle**

```javascript
// Bir önceki çalışma bitmemişse yenisini başlatma
const lock = await redis.set('job:engagement', '1', 'NX', 'EX', 3600);
if (!lock) {
  logger.warn('engagement job already running, skipping');
  return;
}
try { await runJob(); } finally { await redis.del('job:engagement'); }
```

### 23.6 — Katman 6: Dış API Entegrasyonları

**Altın kural:** Dış API (HubSpot, GA4, Clarity, Search Console) **asla** kullanıcı isteğinin veya panel sayfa yüklemesinin içinde çağrılmaz. Cron ile çekilir, lokale yazılır, panel lokalden okur.

```javascript
// ❌ YANLIŞ — panel açılışı HubSpot'u bekler (saniyeler + rate limit riski)
export async function GET() {
  const contacts = await hubspot.crm.contacts.getAll();
  return Response.json(contacts);
}

// ✅ DOĞRU — cron gece çeker, lokale yazar
// cron/syncHubspot.js
async function syncHubspot() {
  let after = null;
  do {
    const page = await hubspot.crm.contacts.basicApi.getPage(100, after);
    await db.insert(hubspotContacts).values(page.results)
      .onConflictDoUpdate({ target: hubspotContacts.hubspotId, set: {...} });
    after = page.paging?.next?.after;
    await sleep(200);   // rate limit'e saygı
  } while (after);
}

// Panel sadece lokal tablodan okur — milisaniye
```

**Rate limit ve hata yönetimi:**

```javascript
async function callWithBackoff(fn, maxRetries = 5) {
  for (let i = 0; i < maxRetries; i++) {
    try { return await fn(); }
    catch (err) {
      if (err.status === 429 || err.status >= 500) {
        await sleep(Math.min(2 ** i * 1000, 30000));  // exponential, max 30sn
        continue;
      }
      throw err;
    }
  }
  throw new Error('max retries exceeded');
}
```

**Dış API sağlık takibi:** Her sync sonrası başarı/hata durumu `integration_health` tablosuna yazılır. Panel "Son sync: X dk önce" bilgisini buradan gösterir; sync başarısızsa Uyarı Merkezi'ne düşer.

### 23.8 — İzlemeyi İzlemek (Meta-Monitoring)

|---|---|
